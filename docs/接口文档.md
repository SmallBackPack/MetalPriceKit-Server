## 一、通用约定

| 项 | 约定 |
|---|---|
| BaseURL | 本地开发 `http://127.0.0.1:8787`；生产待定（`api.metalpricekit.com` 待备案/域名确认） |
| 路径前缀 | `/v1/` |
| 编码 | UTF-8，`application/json; charset=utf-8` |
| 时间 | 一律 ISO 8601 UTC，带 `Z`。例：`2026-11-06T04:42:09.042Z` |
| 数值 | 一律 JSON **number**，不是字符串 |
| 未知字段 | 客户端**必须忽略**服务端新增的未知字段 |
| 响应包裹 | **没有** `{code,message,data}` 包裹层。成败看状态码，业务状态看字段 |

### 1.1 响应头

| 头 | 说明 |
|---|---|
| `X-Request-Id` | 请求追踪 ID，与服务端日志一一对应。用户报障时报这个号 |
| `X-MPK-Encrypted` | `1` = body 是密文信封；`0` = 明文。**客户端按这个头决定要不要解密** |
| `X-MPK-Kid` | 本次响应使用的服务端密钥标识。解密时用它去公钥表里挑公钥 |
| `X-MPK-Mock` | `1` = **服务端当前是假数据模式**（客户端联调用）。真实数据模式下没有这个头 |
| `ETag` | 强 ETag。带 `If-None-Match` 命中返回 304 空 body |
| `Cache-Control` | 按接口设定，见各接口 |

### 1.2 状态码

| 码 | 含义 | 客户端处理 |
|---|---|---|
| 200 | 成功 | 解密 → 解析 |
| 201 | 已创建（反馈） | 解密 → 解析 |
| 204 | 已接收，无 body（崩溃 / 埋点） | 不解密 |
| 304 | ETag 命中 | **不解析 body**，沿用本地缓存 |
| 400 | 参数错误 / 缺客户端公钥 / 信封解不开 | 错误态 |
| 401 | token 无效或过期 | 重新调 auth 换 token，**重试一次** |
| 404 | 路径不存在 | 错误态 |
| 429 | 触发限流 | 读 `Retry-After`，指数退避 |
| 500 | **本服务自身故障** | 错误态 + 重试按钮 |
| 503 | 还没有任何快照（刚启动） | 退避重试 |

> ⚠️ **上游行情源故障不是 5xx。** 走 `200 + isStale: true` ——
> 数据本身是好的，返回 5xx 会让所有用户看到红色错误页。5xx 只代表服务端自己的问题。

### 1.3 鉴权

| 接口组 | 是否需要 token |
|---|---|
| bootstrap / quotes / metals / fx / config / fields / crash | **不需要** |
| profile / feedback / events | **需要** `Authorization: Bearer <token>` |

token 是**归因 + 预留身份**，不是访问控制凭证 —— 客户端可以无限注册。
它解决的是「同一 WiFi 下多人不互相限流」和「反馈能关联到人」，不是「防伪造」。

> **崩溃上报是唯一的例外**，允许匿名 —— 崩溃时客户端可能还没拿到 token。

### 1.4 限流

| 维度 | 阈值 |
|---|---|
| IP | 60 req/min |
| token（仅带 token 的接口） | 30 req/min |

429 响应带 `Retry-After`（秒），照着退避。

### 1.5 加密（简要）

业务接口的响应体是**密文信封**。完整协议与 Swift 实现见
[`客户端接入指南.md`](客户端接入指南.md)。

```json
{ "v": 1, "kid": "k1", "c": "<base64>", "ts": 1793939911289 }
```

`c` 解 base64 后：`nonce(12) || ciphertext || tag(16)`，
算法 X25519 + HKDF-SHA256 + AES-256-GCM，AAD = `方法\n路径\nkid`。

**唯一例外是 bootstrap —— 它是明文**（客户端此时还没有密钥）。

## 三、逐接口

### 3.1 `GET /v1/mpk-bootstrap` — 密钥协商

**明文**，唯一一个不需要解密的接口。客户端拿公钥的唯一途径。

```http
GET /v1/mpk-bootstrap
```

```json
{
  "v": 1,
  "algorithm": "X25519-HKDF-SHA256-AES-256-GCM",
  "keys": [
    { "kid": "k1", "publicKey": "2o1BuxNcS5h8I6Az61sNMTsnKCYi4j6jf3pRFZRHCEU=" }
  ]
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `v` | number | 协议版本 |
| `algorithm` | string | 算法标识，客户端据此选择实现 |
| `keys[].kid` | string | 密钥标识。**解密时用信封里的 `kid` 去这里挑**，不要用下标 |
| `keys[].publicKey` | string | **raw 32 字节 X25519 公钥**的 base64（不是 DER/PEM） |

公钥是长期不变的，可以缓存。**泄露无害**。

### 3.2 `GET /v1/gpwwvvew-deevda` — 行情快照

客户端轮询主力接口。`Cache-Control: no-cache` + ETag（未变返回 304 空 body）。

```http
GET /v1/gpwwvvew-deevda
X-MPK-CK: <客户端公钥 base64>
If-None-Match: "RSwGAW9cT16GsWePvIUB4ufSE5NLG9P1OyQP6oMrYLE"
```

解密后：

```json
{

      "change": -16.93,
      "changeRate": -0.004167,
      "currency": "USD",
      "baseUnit": "oz",
      "scale": 2,
      "asOf": "2026-11-06T04:40:16.203Z",
      "isStale": false
    },
    {
      "code": "XAG",
      "name": "白银",
      "price": 51.474,
      "change": -0.796,
      "changeRate": -0.015229,
      "currency": "USD",
      "baseUnit": "oz",
      "scale": 3,
      "asOf": "2026-11-06T04:40:16.203Z",
      "isStale": false
    },
    {
      "code": "HG",
      "name": "铜",
      "price": 13890.68,
      "change": -439.34,
      "changeRate": -0.030659,
      "currency": "USD",
      "baseUnit": "t",
      "scale": 2,
      "asOf": "2026-11-06T04:40:16.203Z",
      "isStale": false
    }
  ]

```

**实际返回 8 个品种**（上面只列了 3 个作示例）。完整品种见 §四。

| 字段 | 类型 | 说明 |
|---|---|---|
| `serverTime` | string | 服务端响应时刻（UTC） |
| `marketStatus` | string | `open` / `closed`。契约预留了 `pre` / `after`，服务端暂不下发 → **未知值按 `open` 处理** |
| `changeBasis` | string | 涨跌基准，固定 `prevClose`（服务端自算的上一交易日收盘价） |
| `dataSource` | string | `live` = 真实上游；**`mock` = 假数据（客户端联调模式）** |
| `quotes[].code` | string | 品种代码，与 `metals` 里的 `code` 关联 |
| `quotes[].name` | string | 中文名 |
| `quotes[].price` | number | **USD 基准价**，单位是 `baseUnit` |
| `quotes[].change` | number | 涨跌额，单位同 `baseUnit`。周末冻结时沿用上一交易日 |
| `quotes[].changeRate` | number | **原始小数**，`-0.004167` = -0.4167%。**不乘 100** |
| `quotes[].currency` | string | 固定 `USD`。换算在客户端做 |
| `quotes[].baseUnit` | string | 报价所依附的质量单位，`oz` 或 `t`。**与 `price` 成对使用** |
| `quotes[].scale` | number | 该价格在 `baseUnit` 下的显示小数位 |
| `quotes[].asOf` | string | 该品种上游价格时间戳（逐条给） |
| `quotes[].isStale` | boolean | 逐条给。`true` 表示采集器很久没抓到新数据 |

**客户端硬规则**：

1. `price` 与 `baseUnit` **成对用**。不要假设 `HG` 一定是吨 —— 以接口下发的为准。
2. `changeRate` 是小数，渲染时才乘 100。
3. `change` 的单位是 `baseUnit`。铜的涨跌额是 USD/**吨**，不是 USD/磅。
4. **缺某个品种就是缺了** —— 不要用 0 兜底，列表里少一条就少一条。
5. `marketStatus` 未知值按 `open` 处理，不要崩。


| 字段 | 说明 |

### 3.4 `GET /v1/tqzxvnrk-lzbor` — 汇率表

客户端冷启动拉一次。`Cache-Control: max-age=3600`。

```json
{
  "serverTime": "2026-11-06T04:42:09.060Z",
  "base": "USD",
  "asOf": "2026-11-06T04:39:12.262Z",
  "rates": {
    "USD": 1,
    "CNY": 6.67049061,
    "CNH": 6.66697705,
    "EUR": 0.89303673,
    "JPY": 157.9253461,
    "HKD": 7.83546704,
    "KRW": 1356.82485616
  }
}
```

**实际返回 155 个币种**（上面只列了 7 个作示例）。

| 字段 | 说明 |
|---|---|
| `base` | 固定 `USD`。显式声明方向，防止客户端搞反 |
| `asOf` | 汇率的上游时间戳 |
| `rates` | 语义：**1 USD = `rates[X]` 个 X 币** |

- 服务端**不提供** `?currency=` 参数 —— 服务端和客户端同时换算会产生两套口径，迟早对不上。
- 汇率已收敛到 8 位小数，不会出现 `3.6725000000514147` 这种浮点尾巴。

**客户端换算链（顺序固定）**：

```
原始价 usdPrice (USD, baseUnit)
  → ① 单位换算：MKFormatter.convert(usdPrice, from: baseUnit, to: 用户所选单位)
  → ② 币种换算：× rates[targetCurrency]
```

**顺序固定「先单位、后币种」** —— `scale` 绑定在「该单位下的价格」上，顺序反了精度会错。

> ⚠️ **接入前必须先修客户端的单位换算系数。**
> `MKMetalUnit.ouncesPerUnit` 的 `.ton` 目前用的是**美制短吨**（29166.6667 盎司），
> 而中文「吨」是**公吨**（1,000,000 g = **32150.7466 金衡盎司**），系数偏小 9.28%，
> 换算出的每盎司价格偏高 10.24%。铜 13890.68 USD/t 现在会算出 0.47625，正确是 0.43205。
> 修法：`case .ton: return 1000 * MKMetalUnit.kilogram.ouncesPerUnit`
> **服务端只发 USD 基准价，单位换算全在客户端 —— 这条不修，服务端数据再准，显示的也是错的。**

### 3.5 `GET /v1/wqbdtoe-ocfvy` — 结构化配置

强类型结构，客户端按强类型解码。`Cache-Control: max-age=300`。

```json
{
  "serverTime": "2026-11-06T04:42:09.063Z",
  "configVersion": 1,
  "features": {
    "showGuide": true,
    "guideVersion": 1,
    "enableConverter": true,
    "enableMetalDetail": true
  },
  "runtime": {
    "pollIntervalSeconds": 15,
    "upstreamRefreshSeconds": 600
  },
  "app": {
    "minSupportedVersion": "1.0.0",
    "latestVersion": "1.0.0",
    "updateUrl": ""
  },
  "marketing": {
    "bannerText": "",
    "bannerUrl": "",
    "noticeTitle": "行情数据说明",
    "noticeContent": "本应用行情来自第三方数据源，可能存在延迟，仅供参考，不构成投资建议。"
  }
}
```

| 字段 | 说明 |
|---|---|
| `configVersion` | 配置版本号。变了就刷新本地缓存 |
| `features.showGuide` | 是否显示引导页 |
| `features.guideVersion` | 引导页版本号。客户端本地记 `lastGuideVersion`，小于服务端就显示引导 |
| `runtime.pollIntervalSeconds` | **客户端轮询我们**的间隔建议。当前 15 秒 |
| `runtime.upstreamRefreshSeconds` | **我们拉上游**的间隔 —— 数据本身多久更新一次。当前 600 秒 |
| `app.minSupportedVersion` | 低于此版本强制提示升级 |
| `marketing.*` | 营销横幅 + 公告文案。**空字符串表示不展示**（不要用 `nil` 语义区分） |

> ⚠️ **`pollIntervalSeconds` 短不代表数据新。**
> 客户端 15 秒轮询一次我们的服务器，但我们的数据是**上游刷新周期**（`upstreamRefreshSeconds`）决定的。
> 免费档下上游额度只够约 7 小时刷新一次，**所以现在数据的新鲜度以小时计**。
> UI 上要靠 `asOf` 表达「数据更新于 X 分钟前」，别让用户以为是秒级实时。

> `features` / `marketing` / `runtime.pollIntervalSeconds` 的值来自服务端的通用配置文件，
> 运维改文件即生效，**不用发客户端版本**。

### 3.6 `GET /v1/rtkbmvxw-pflqs` — 通用字段字典

**这就是你要的「[key: Any] 通用字典」。** 解密后就是一个扁平的 JSON 对象，
结构完全由数据决定 —— 服务端加字段不用改代码、不用发客户端版本。

```json
{
  "pollIntervalSeconds": 15,
  "staleAfterMinutes": 30,
  "features": {
    "showGuide": true,
    "guideVersion": 1,
    "enableConverter": true,
    "enableMetalDetail": true
  },
  "marketing": {
    "bannerText": "",
    "bannerUrl": "",
    "noticeTitle": "行情数据说明",
    "noticeContent": "本应用行情来自第三方数据源，可能存在延迟，仅供参考，不构成投资建议。"
  },
  "units": {
    "default": "base",
    "allowed": ["base", "oz", "g", "kg", "lb", "t"]
  },
  "currencies": {
    "default": "CNY",
    "allowed": ["CNY", "CNH", "USD", "EUR", "JPY", "HKD", "GBP", "KRW", "TWD"]
  },
  "experimental": {
    "remoteFieldsEnabled": true
  }
}
```

约定：

- 顶层是对象，值可以是任意 JSON 值（字符串 / 数字 / 布尔 / 数组 / 嵌套对象 / null）。
- **客户端必须忽略不认识的 key**（老版本遇到新字段不能崩）。
- 服务端不下发 `configVersion` 和下划线开头的 key（那是元信息）。
- 客户端用 `[String: Any]` 解码（Swift 侧就是 `JSONSerialization`，或 `Codable` + `AnyCodable`）。

> `config` 与 `fields` **不是两份独立数据** —— 同一份配置文件的两种交付方式。
> `config` 是强类型结构（客户端写死 Decodable），`fields` 是通用字典（客户端按需取）。

### 3.7 `POST /v1/nrmlkzvc-xdpwo` — 匿名身份

**不需要登录页。** 客户端首次启动自动调用，服务端自动建用户并发 token。
`deviceId` **幂等**：同一 deviceId 重复调用返回同一 `userId` + **新 token**。

请求：

```json
{
  "deviceId": "B3F1A2C4-8E2D-4A19-9C77-1D0E5F6A7B88",
  "appVersion": "1.0.0",
  "build": "100",
  "osVersion": "18.0",
  "locale": "zh-Hans",
  "deviceModel": "iPhone16,2"
}
```

只有 `deviceId` 是必需的（1–128 字符），其余字段服务端收下但不用。

响应 200：

```json
{
  "userId": "u_f87fc42a",
  "token": "4ac64593d5856cbb3ae5d3b9e3336fa00b78b332789f47f7c396eed2a6e8e9bb",
  "expiresAt": "2027-11-06T04:42:09.086Z",
  "isNewUser": true,
  "profile": {
    "nickname": "用户 f87f",
    "settings": {}
  }
}
```

| 字段 | 说明 |
|---|---|
| `userId` | 用户 ID，`u_` + 8 位 hex |
| `token` | 随机 32 字节（64 hex）。**服务端只存 SHA-256 哈希**，不存明文 |
| `expiresAt` | 有效期 **1 年**。过期后重新调本接口即可，**不需要单独的 refresh 接口** |
| `isNewUser` | 首次 `true`，之后 `false`（客户端可用它决定是否弹引导页） |
| `profile.settings` | 偏好。默认 `{}`（客户端自己存默认值也行） |

- **旧 token 保留到自然过期，不主动吊销** —— 否则客户端并发请求时会互相踢掉。
- 客户端的 `deviceId` 用 `identifierForVendor` 存 Keychain。
  （注意：`identifierForVendor` 在用户卸载重装后会变，正好符合「重装即新用户」的预期。）

## 五、错误响应

错误响应体（未加密）：

```json
{ "error": "bad_request" }
```

`error` 是**字符串枚举**，不是数字。客户端要按未知值兜底，不能崩。

| `error` | 状态码 | 含义 |
|---|---|---|
| `bad_request` | 400 | 参数错误 / 信封解不开 |
| `client_key_required` | 400 | 没有 `X-MPK-CK` 头，或公钥不合法 |
| `invalid_device_id` | 400 | deviceId 为空或超过 128 字符 |
| `invalid_content` | 400 | 反馈内容为空 |
| `unauthorized` | 401 | token 无效或过期 |
| `not_found` | 404 | 路径不存在 |
| `too_many_requests` | 429 | 限流。看 `Retry-After` |
| `internal_error` | 500 | 服务端自身故障 |
| `snapshot_unavailable` | 503 | 还没有任何快照（刚启动、还没抓到数据） |

## 六、客户端必须遵守的硬规则（速查）

1. **不知道的字段一律忽略。** 服务端会加字段，客户端不能因此崩。
2. **`changeRate` 不乘 100。**
3. **`price` 和 `baseUnit` 成对用。**
4. **404 就是路径不对**（不是你拼错了参数）。语义路径服务端不存在。
5. **400 `client_key_required` = 你的 `X-MPK-CK` 头没发或格式不对。**
6. **解密失败先查 AAD**：`method`、`path`、`kid` 三段必须与服务端逐字节一致，
   尤其注意 `path` 不含查询串。
7. **上游故障不是错误态。** `200 + isStale: true` 是正常返回，走弱化显示。
8. **401 重新换 token 重试一次**，不要无限重试。profile / feedback / events 都要 token。
9. **token 存 Keychain**，`deviceId` 用 `identifierForVendor`。
10. **崩溃上报必须吞掉所有错误。**
11. **`marketStatus` 未知值按 `open` 处理。**
12. **单位换算先单位、后币种**，且 `.ton` 的系数要先修对（见 §3.4 的警告）。

## 八、当前联调环境跑的是假数据

服务端现在开着**假数据模式**（`MPK_MOCK=true`）：

- **不请求上游，不消耗额度。** 上游免费档一个月只有 100 次，
  联调打真实上游几天就烧光了，而额度要等下个月才重置。
- **接口形状、加密、字段全是真的** —— 只有价格是模拟的。
  所以联调通过的部分，切回真实数据后不用重测。
- **价格每 15 秒变一次**（随机游走），客户端的刷新逻辑能真的看到数据在动。
- **涨跌额不是 0** —— 服务端给假数据播了一份「上一交易日收盘价」当基准。

### 怎么认出这是假数据

| 位置 | 标记 |
|---|---|
| 响应头 | `X-MPK-Mock: 1`（每个响应都有，包括 400/401） |
| body | `quotes[].dataSource` 的值是 `"mock"`（真实数据是 `"live"`） |

**客户端建议**：读 `dataSource`，是 `mock` 就显示一个「模拟数据」角标。
联调用的 App 万一被误当成正式版发出去，能一眼认出来。

### 跟真实数据的差异

| | 假数据 | 真实上游 |
|---|---|---|
| 币种数 | 26 | 155 |
| 价格 | 随机游走 | 真实行情 |
| 刷新间隔 | 15 秒 | 取决于套餐配额（免费档约 7 小时） |
| 上游额度 | 0 | 每次轮询扣 1 |

联调通过后，服务端把 `MPK_MOCK` 改成 `false` 重启即可切回真实数据，
**客户端代码一行都不用改**。
