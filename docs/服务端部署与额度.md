# 服务端部署与额度

> 面向运维（Chaoz 本人）。本文只讲三件事：**怎么部署上去**、**额度怎么花不爆**、
> **额度决定了产品能承诺什么**。

---

## 〇、先看这一条：额度决定了产品承诺

**上游免费档是 100 次/月。** 这不是技术问题，是产品问题 —— 必须在写文案之前想清楚。

| 套餐 | 价格 | 每月请求数 | 平均刷新间隔 |
|---|---|---|---|
| Free | $0 | 100 | **约 7 小时** |
| Copper | $1.49/月 | 2,000 | 约 21 分钟 |
| Silver | $9.99/月 | 10,000 | 约 4 分钟 |

算法：一个月按 30 天算，`43200 分钟 ÷ 月请求数`。

### 这意味着什么

- ❌ **不能对外宣称「实时行情」或「秒级更新」。** 免费档下一个用户看到的数字，
  可能是 7 小时前的。
- ❌ **不能承诺「每天多次更新」以外的东西。** 100 次 ÷ 30 天 = 每天 3.3 次。
- ✅ **可以承诺「数据来自专业行情源，价格准确」。** 这是本 App 的真正卖点。
- ✅ **App 的轮询频率不受上游限制** —— 客户端 15 秒轮询我们的服务器，
  我们从本地缓存返回，**不消耗上游额度**。所以体验上「秒开秒有」是可以的，
  只是数字本身的更新粒度受上游限制。

### 建议的取舍

| 阶段 | 套餐 | 理由 |
|---|---|---|
| 内测 / 开发 | Free | 省着点用，把额度留给调试 |
| 上架前 | **Copper $1.49** | 21 分钟粒度，配上「数据可能延迟」的提示，基本够用。$1.49/月换「每小时至少更新一次」，很划算 |
| 用户量上来 / 有人抱怨数据不新 | Silver $9.99 | 4 分钟粒度，基本可以叫「准实时」 |

升级只要改两个环境变量，**不用改代码、不用重启**：

```bash
MPK_MONTHLY_BUDGET=2000
MPK_POLL_INTERVAL_MS=900000      # 15 分钟
```

### ⚠️ 上架前必须确认：授权范围

metals.dev 条款写的是 **"publish rates on websites"**。
**在 iOS App 内展示行情，是否等同于「on websites」，条款里没写清楚。**

- 这是上架前的硬门槛，不是技术问题。
- **动作**：发邮件给 metals.dev 问清楚 —— "Do you permit displaying your metal rates inside a native mobile application (iOS/Android)?"
- 问不到明确答复前，**不要上架**，也不要在 App 里写「数据来自 metals.dev」。

## 一、部署形态

```
        ┌──────────────┐        ┌──────────────┐
客户端 ──│ Nginx        │───────▶│ Node 服务     │──▶ metals.dev
  (TLS) │ 443 → 8787   │  HTTP  │ (systemd)    │    (100 次/月)
        │ gzip         │        │ :8787        │
        │ limit_req    │        └──────────────┘
        └──────────────┘
```

- **Node 只监听 `127.0.0.1:8787`**，公网只开 Nginx。
- **TLS 在 Nginx 层**。服务端本身不做 HTTPS —— 加密是应用层的，
  再套一层 TLS 属于双保险，不是必需。
- **2 核 4G / 40GB SSD 绰绰有余。** 这台服务的常驻内存大约 60–80MB
  （主要是 Node 运行时 + SQLite 缓存），CPU 占用在空闲时接近 0。

### 1.1 安装 Node

用 Node 22 LTS 或更高（需要 `node:sqlite` 与原生 TS 执行）。
开发机上装的是 Node 26.13，服务器照这个版本即可。

```bash
curl -fsSL https://nodejs.org/dist/v26.13.0/node-v26.13.0-linux-x64.tar.xz \
  | tar -xJ -C /usr/local --strip-components=1
```

### 1.2 拉代码 + 装依赖

```bash
sudo mkdir -p /opt/metalpricekit-server && sudo chown $USER /opt/metalpricekit-server
cd /opt/metalpricekit-server
git clone <仓库地址> .
npm install --omit=dev
```

> 生产只需要 `express` 一个运行时依赖。
> **不需要构建步骤** —— Node 26 直接执行 `.ts`（`node src/index.ts`）。
> 这也是当初选 Node 的原因之一：省掉 tsx/ts-node/tsc 三件套。

### 1.3 环境变量文件

`/etc/metalpricekit-server.env`（`chmod 600`）：

```bash
NODE_ENV=production
PORT=8787
HOST=127.0.0.1

METALS_DEV_API_KEY=<你的 key>

# 每月额度上限（硬刹车）。跟套餐档位对齐。
MPK_MONTHLY_BUDGET=100
# 轮询间隔下限（毫秒）。实际间隔 = max(这个值, 额度刹车算出来的间隔)。
MPK_POLL_INTERVAL_MS=600000

# 服务端长期密钥。生成方法见第二节。
MPK_SERVER_KEYS=k1:<base64 的 32 字节私钥>
MPK_ACTIVE_KID=k1

MPK_DATA_DIR=/opt/metalpricekit-server/data
MPK_REMOTE_CONFIG_FILE=/opt/metalpricekit-server/config/remote-config.json
```

**`NODE_ENV=production` 必须设。** 不设的话服务端不会强制加密 ——
没有客户端公钥的请求会拿到明文数据，加密形同虚设。

### 1.4 systemd

`/etc/systemd/system/metalpricekit-server.service`：

```ini
[Unit]
Description=MetalPriceKit Server
After=network.target

[Service]
Type=simple
User=mpk
WorkingDirectory=/opt/metalpricekit-server
EnvironmentFile=/etc/metalpricekit-server.env
ExecStart=/usr/local/bin/node src/index.ts
Restart=always
RestartSec=5

# 采集器是自己算好时间才醒的，不要被定时器钉住。
KillSignal=SIGTERM
TimeoutStopSec=10

StandardOutput=journal
StandardError=journal
SyslogIdentifier=metalpricekit-server

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now metalpricekit-server
sudo journalctl -u metalpricekit-server -f
```

日志是**单行 JSON**，直接进 journald，`journalctl -o cat | jq` 就能查。

### 1.5 Nginx

```nginx
server {
    listen 443 ssl http2;
    server_name api.example.com;

    ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;

    # 压缩密文收益不大，但 bootstrap 的公钥表和品种字典压一下没坏处。
    gzip on;
    gzip_types application/json;

    # IP 层限流兜底。应用层还有一层，两层都留着。
    limit_req_zone $binary_remote_addr zone=mpk:10m rate=60r/m;

    location / {
        limit_req zone=mpk burst=20 nodelay;
        limit_req_status 429;

        proxy_pass http://127.0.0.1:8787;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 客户端要拿到真实 IP，限流才准（Express 的 req.ip 依赖它）。
        proxy_read_timeout 30s;
    }
}

server {
    listen 80;
    server_name api.example.com;
    return 301 https://$host$request_uri;
}
```

> **限流两处都有**：Nginx 按 IP（60/min），应用内按 token（30/min）。
> 应用层的 IP 限流是兜底 —— 万一 Nginx 配漏了，还有应用层挡着。

## 二、密钥管理与轮换

### 2.1 生成

```bash
node -e "console.log('k1:'+require('crypto').randomBytes(32).toString('base64'))"
```

输出形如 `k1:3vJ9...`（base64 的 32 字节私钥）。**这个值就是服务端的全部秘密**，
泄露 = 所有历史响应在知道私钥的前提下都可被伪造。存进 env 文件，`chmod 600`。

### 2.2 公钥怎么给客户端

**不用管** —— 客户端调 `GET /v1/mpk-bootstrap` 就拿到公钥。那是明文接口，
只暴露公钥，泄露无害。

### 2.3 轮换

轮换 = 换一把新私钥重新签发。

```bash
# 1. 生成新密钥
node -e "console.log('k2:'+require('crypto').randomBytes(32).toString('base64'))"

# 2. 改 env：两把并存，activeKid 指向新的
MPK_SERVER_KEYS=k1:<旧的>,k2:<新的>
MPK_ACTIVE_KID=k2

# 3. 重启
sudo systemctl restart metalpricekit-server
```

轮换期间：

- `bootstrap` 会同时返回 k1 和 k2 的公钥。
- 响应一律用 k2 加密，信封里的 `kid` 写 `k2`。
- 客户端**按信封里的 kid 选公钥**（见客户端接入指南 §4.3），所以老客户端只要还没重启也能解。
- 客户端的**请求**用哪把都行 —— 服务端按请求信封里的 `kid` 挑自己的私钥。

**注意事项**：

- 私钥一旦生成就要备份好。**丢了就解不开所有历史缓存的响应**。
- 轮换不需要客户端发版（公钥表是运行时拿的），
  但**要确认客户端是按 `envelope.kid` 选公钥**而不是按数组下标 —— 后者会在轮换时集体失败。

## 三、额度账本与刹车

### 3.1 实测到的上游计费规则（2026-11）

| 路径 | 扣额度 | 说明 |
|---|---|---|
| `GET /v1/latest` | **扣 1** | 一次拿回全部 8 金属 + 全部汇率 |
| `GET /v1/metal/spot` | **扣 1** | 只覆盖一个品种，**没有批量版** |
| `GET /usage` | **不扣** | 随便查，用来对账 |

所以：**只用 `/v1/latest`，一次请求顶 8 次。**
逐品种调 `spot` 拿官方昨收（8 次/轮）在这个额度下完全不可行。

### 3.2 三重保护

| # | 机制 | 在哪 | 防的是什么 |
|---|---|---|---|
| 1 | 本地 SQLite 记账 | `usage_counter` 表 | 进程重启不丢计数。**崩溃循环烧光额度** |
| 2 | 硬预算刹车 | `src/upstream.ts` | 超过 `MPK_MONTHLY_BUDGET` 直接拒绝发请求，**不真发** |
| 3 | 平台侧对账 | `GET /usage` | 请求「发出去了但没收到响应」时平台已扣、本地不知道。**宁可多算不能少算** |

第 3 条的逻辑：本地计数只知道自己发了几次。额度是硬约束，
少算意味着某个月会突然被断供，而且**断供的时候你不知道为什么**。

### 3.3 刹车算法

```
剩余秒数 ÷ 剩余配额 = 每次调用至少要隔多久
实际间隔 = max(MPK_POLL_INTERVAL_MS, 上面算出来的值)
```

例：11 月 4 日，剩 26 天、剩 99 次额度 → `26×86400 ÷ 99 ≈ 6.3 小时`。
所以那一轮采集安排在 6.3 小时后，而不是配置的 10 分钟后。

**预算耗尽时**退到 1 小时一轮（`src/collector.ts`），
这样月初额度重置后能自动恢复，而不是彻底停摆。

### 3.4 对账

```bash
curl "https://api.metals.dev/usage?api_key=$METALS_DEV_API_KEY"
```

返回 `{ plan, total, used, remaining }`。**这个调用不扣额度**，随时可以查。

对账逻辑在 `src/store.ts` 的 `syncUsage()`：**平台用量 > 本地计数时，用平台的值覆盖本地**。

建议加个定时任务，每天对一次账并把结果记到日志：

```bash
0 9 * * * curl -s "https://api.metals.dev/usage?api_key=$METALS_DEV_API_KEY" >> /var/log/metalpricekit-usage.log
```

### 3.5 采集失败怎么办

**保留上一份快照继续对外服务**，不报错、不返回 5xx。

- 契约明确要求：上游行情源故障走 `200 + isStale: true`。
- 返回 5xx 会让所有用户看到红色错误页，而数据本身是好的。
- `isStale` 的判定用的是**我们上次成功抓取的时间**，不是上游时间戳 ——
  免费档轮询间隔必然以小时计，按上游时间戳 + 30 分钟判会导致所有品种永远过期。

## 四、环境变量总表

| 变量 | 默认值 | 说明 |
|---|---|---|
| `NODE_ENV` | 无 | **生产必须设 `production`**。不设则不强制加密 |
| `PORT` | `8787` | 监听端口 |
| `HOST` | `0.0.0.0` | 生产建议 `127.0.0.1`，公网只走 Nginx |
| `METALS_DEV_API_KEY` | 空 | 上游 key。空则服务仍可启动（用本地快照对外服务），但不会更新 |
| `METALS_DEV_BASE_URL` | `https://api.metals.dev` | 换供应商改这个 + `config/metals.json` 的符号映射 |
| `MPK_MONTHLY_BUDGET` | `100` | 每月硬上限。**改套餐时改这里** |
| `MPK_POLL_INTERVAL_MS` | `600000` | 轮询间隔下限。实际间隔会被额度刹车拉长 |
| `MPK_SERVER_KEYS` | 无 | **必填**，格式 `k1:<base64>,k2:<base64>` |
| `MPK_ACTIVE_KID` | `k1` | 当前生效的密钥标识，必须在 `MPK_SERVER_KEYS` 里 |
| `MPK_FETCH_ON_BOOT` | `true` | 启动时立刻拉一次上游。**消耗 1 次额度**，无本地快照时别关 |
| `MPK_DATA_DIR` | `data` | SQLite 存放目录 |
| `MPK_REMOTE_CONFIG_FILE` | `config/remote-config.json` | 通用字段字典文件 |

## 五、排查手册

| 现象 | 查什么 |
|---|---|
| 价格半天不变 | `journalctl -u metalpricekit-server \| grep 已安排下一轮采集` 看安排的间隔是不是被刹车拉长了 |
| 某个品种没了 | 看日志里 `采集成功` 的 `metals` 数量。少了说明上游没返回该品种 |
| 客户端报 400 `client_key_required` | 客户端没发 `X-MPK-CK` 头，或 base64 不是 32 字节 |
| 客户端解密失败 | **先查 AAD**：`method` / `path` / `kid` 三段是否与服务端逐字节一致 |
| 401 | token 过期。让客户端重新调 auth（幂等，会给新 token） |
| 429 | 看 `Retry-After`。IP 限流 60/min、token 限流 30/min |
| 503 `snapshot_unavailable` | 服务刚起来还没抓到第一份快照。看 `lastFetchOk` |
| 额度莫名其妙少 | 跑一次 `/usage` 对账。本地计数和平台对不上就说明有「发出去了但没回来」的请求 |
| 日志中文乱码 | 日志文件本身是 UTF-8，是查看工具按 ANSI 读的。`Get-Content -Encoding UTF8` / `jq` 都正常 |

### 5.1 手工验证加解密链路

```bash
node scripts/smoke.ts https://api.example.com
```

输出「自检通过」就说明线上这一整条链路是通的（bootstrap → ECDH → HKDF → AES-GCM → 解密）。

### 5.2 本地跑起来

```bash
export METALS_DEV_API_KEY=<key>
export MPK_SERVER_KEYS=$(node -e "console.log('k1:'+require('crypto').randomBytes(32).toString('base64'))")
node src/index.ts
```

然后：

```bash
node scripts/smoke.ts http://127.0.0.1:8787
```

## 六、备份

| 内容 | 位置 | 丢了会怎样 |
|---|---|---|
| 服务端私钥 | env 文件 | **历史响应全废**，必须重新生成并通知客户端 |
| `market.db` | `data/market.db` | 丢失「上一交易日收盘价」→ 涨跌基准丢失，涨跌显示为 0（**要等一个交易日才恢复**） |
| `user.db` | `data/user.db` | 丢失用户资料与 token → 用户要重新注册（匿名用户，影响不大） |

`market.db` 值得备份 —— 它积累的是**服务端观测到的历史价格**，
是涨跌额的数据基础，重建需要时间。建议每天 cron 拷一份：

```bash
0 4 * * * sqlite3 /opt/metalpricekit-server/data/market.db ".backup '/backup/market-$(date +\%F).db'"
```

## 七、还没做的（v1 明确不做的）

| 事项 | 原因 |
|---|---|
| Redis / 多实例 | 单机单进程够用。用户量涨了再说 |
| 汇率历史 / 走势图接口 | 客户端没有对应 UI |
| 附件上传 | 反馈附件走对象存储直传，不经服务端 |
| 推送 token 注册 | v1 不做推送 |
| Redis 缓存 | 本地 SQLite 已经够快 |
